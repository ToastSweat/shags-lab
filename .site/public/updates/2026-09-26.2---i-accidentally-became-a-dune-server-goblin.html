I Accidentally Became A Dune Server Goblin

This started because I wanted a private Dune server.

That seems simple enough.

Install the dedicated server.
Set a password.
Invite friends.
Run around Arrakis.
Try not to get eaten by the worm.

Naturally, I ended up learning about SteamCMD, Hyper-V networking, Windows NAT, Kubernetes pods, container images, UDP port ranges, memory limits, broken upstream builds, and the emotional burden of naming an internal switch Bootyhole.

This happens to me a lot.

At that point, the evidence was pretty clear:

Funcom had pushed a bad self-host build.

Honestly, that was kind of a relief.

It is annoying when something is broken upstream, but it is also nice to stop gaslighting yourself with port forwarding rules.

I sent an email through the Funcom site.

Discord pointed me that way.

Eventually, Funcom fixed the build.

It did not fix itself automatically.

A normal restart did not fix it.

I had to run the server update again, pull the corrected build, and restart the battlegroup.

Then everything came back.

Actual game rows.
Actual status.
Actual server visibility.
Actual joy.

What did I learn?

I learned that self-hosting modern games is not just “run server.exe.”

It is a stack.

A weird stack.

A Windows host runs a Linux VM that runs Kubernetes that runs containers that run the game servers that talk through gateways that depend on RabbitMQ and a database and a director and a handful of UDP ports that all need to agree about reality.

That sentence is exhausting.

The server is up.
The bad battlegroup is gone.
The network setup is documented.
The weird Funcom build failure is documented.
The recovery path is documented.

And most importantly:

Not bad for wanting to play Dune with friends.
