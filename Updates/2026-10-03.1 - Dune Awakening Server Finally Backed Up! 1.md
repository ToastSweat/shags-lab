This started because my base was running out of power.

We have not really been playing Dune lately, and I did not want the server quietly chewing through fuel while nobody was online.

So I had a simple question:

> Can I put Arrakis into hibernation?

The answer was basically yes.

Stop the battlegroup.
Power off the VM.
Nothing is actively simulating the desert anymore.

Beautiful.

Then I had a second question.

> If this entire server explodes six months from now, can I actually bring our world back?

That answer was much less comforting.

I already had a doomsday guide for rebuilding the server itself. It documents the Windows host, Hyper-V, the internal switch named `Bootyhole`, Windows NAT, port forwarding, the Funcom setup, Kubernetes, and all the other machinery required to turn a dedicated Windows server into a private Arrakis.

But knowing how to rebuild the machine is not the same thing as preserving the world.

I wanted to know that we could keep:

- player characters
- inventories
- bases
- land claims
- vehicles
- container contents
- world state
- database changes
- and all of the custom tuning that makes the server less miserable for one or two people

I did not want the recovery plan to be:

```text
Here is one enormous mystery file.
Throw it at Hyper-V and pray.
```

I wanted a clean-install recovery package.

Install a fresh server.
Restore the important data.
Put the configuration back.
Continue exactly where we left off.

That seems simple enough.

Naturally, this turned into another expedition through Kubernetes, PostgreSQL, persistent volumes, container images, Linux ownership metadata, Windows NAT, SHA-256 checksums, and one completely unnecessary 97 GB virtual machine export.

This also happens to me a lot.

## First: Stop Time

The real battlegroup is:

```text
sh-238803c537a22e2-fdofyf
```

That pile of letters contains the actual world.

The first step was stopping it cleanly.

This matters because the running game servers hold state in memory and write it back to PostgreSQL during shutdown.

I already learned this while manually filling our base cisterns.

I changed the database while the game was running.

The database said:

```text
400,000 water
```

The game said:

```text
lol no
```

Then the server shut down and saved its old in-memory values back over my changes.

The successful method was:

```text
Stop battlegroup
Edit persistent data
Start battlegroup
```

So for the backup, the game servers stayed stopped while PostgreSQL remained available.

That gave us a clean snapshot instead of a database arguing with a live game process about which version of reality was correct.

## The Important Part Is Surprisingly Small

The Funcom utility has an official database backup operation.

On the current build, that is menu option:

```text
10. backup
```

It created:

```text
sh-238803c537a22e2-fdofyf-20261003-015515.backup
sh-238803c537a22e2-fdofyf-20261003-015515.backup.yaml
```

The PostgreSQL dump was only about 1.4 MB.

That initially felt suspiciously tiny for an entire world full of buildings, characters, inventories, vehicles, and all of my terrible decisions.

But the important Dune state is structured database data. It is not a giant pile of traditional world-save files.

The database contains the things I actually care about:

- players and characters
- inventories and items
- placed structures
- bases and ownership
- vehicles
- world actors
- generic component state
- stored resources
- and the other persistent records that make our world our world

I validated the dump with `pg_restore --list`.

It returned:

```text
VALID: pg_restore parsed the backup successfully
```

That was the first genuinely reassuring moment of this project.

The backup was not just present.

PostgreSQL could actually read it.

## Then I Started Collecting Every Other Important Piece

The database is the heart of the recovery, but it is not the entire server personality.

The custom tuning lives in:

```text
UserEngine.ini
UserGame.ini
```

Those files contain the changes that make the server reasonable for a tiny group instead of balanced around a permanently populated public server.

Mining multipliers.
Vehicle mining.
PvP resource behavior.
Sandstorms.
Worm behavior.
Building limits.
Land claim extensions.
All the weird little discoveries we have made while experimenting.

I copied both the live files actually mounted into the battlegroup and the setup-template versions stored by the installer.

Then I exported the Kubernetes side of the setup:

- Funcom custom resources
- the battlegroup specification
- persistent volume claims
- persistent volumes
- workloads
- ConfigMaps
- container image references
- VM and network information

I also archived the battlegroup's persistent `/srv` storage.

That includes the live user settings, logs, crash reports, database dump history, and the other files living on the battlegroup volume.

The persistent archive contained:

```text
102 entries
```

Then every file in the recovery folder got its own SHA-256 checksum.

The final portable bundle contained:

```text
database/
config-live/
config-setup/
kubernetes/
system/
battlegroup-persistent-files.tar.gz
BACKUP-INFO.txt
SHA256SUMS.txt
```

And after all of that, the complete portable recovery package was only:

```text
7,836,960 bytes
```

About 7.5 MB.

That tiny file is the actual important backup.

It is the part that can rebuild the world on a clean installation without dragging an entire old operating system behind it.

Its SHA-256 is:

```text
f46c95b0468570b408cc64ed75769ac6016b288dd27b3ba9bde7ebf0351a5c4d
```

I copied it out of the Linux VM and verified the Windows copy against the original hash.

This was slightly more annoying than expected because the VM did not have an SFTP server and also did not have the remote `scp` command.

The modern transfer method failed.

The legacy transfer method failed.

So naturally the working solution was basically:

```text
SSH into the VM
cat the binary file
redirect it into a file on Windows
```

Elegant?

No.

Did the hashes match?

Yes.

And that is the kind of elegance I care about.

## Backing Up the Windows Host Without Backing Up Windows

I also wanted enough information to recreate the host configuration without cloning the entire host.

So I captured:

- Hyper-V VM settings
- assigned memory and processors
- network adapters
- virtual switches
- virtual hard disk information
- Windows NAT configuration
- every NAT port mapping
- Windows IP addresses
- the exported Windows Firewall policy
- Windows system information

That became a separate ZIP file.

Its size was:

```text
40,757 bytes
```

Forty kilobytes.

That is much closer to what I had in mind.

The host configuration explains how to rebuild the machine.

The portable Dune bundle restores the world.

The doomsday guide explains how the pieces fit together.

Reasonable.

Portable.

Actually useful.

## Then We Made the Big Boi

At some point, the disaster-recovery plan drifted from:

> Preserve the unique data required for a clean rebuild.

to:

> What if we also export the entire virtual machine?

This is where communication may have broken down slightly.

The VM reported only around 28 GB of currently used data inside Linux.

The Hyper-V virtual disk had grown to:

```text
96.82 GB
```

Dynamic virtual disks grow when blocks are used, but they do not necessarily shrink when files are later deleted.

So the disk was carrying years of emotional baggage in the form of allocated blocks.

I cleaned enough space on the Windows host, powered the VM off, and started a cold Hyper-V export.

Then I saw the size.

My immediate technical assessment was:

> holy crap, why is it so big

Followed immediately by:

> that's what she said

The export finished successfully.

It contained four files, almost all of which was the 96.82 GB VHDX.

I ran:

```powershell
Test-VHD
```

It returned:

```text
True
```

So the big boi is valid.

It is also absolutely not the normal backup plan.

The giant Hyper-V export is temporary emergency insurance until I perform a full clean-install restore rehearsal.

The 7.5 MB portable package is the thing future me is supposed to use.

One backup is a carefully packed emergency kit.

The other backup is the entire house lifted onto a trailer.

Both technically solve the problem.

Only one is going to fit in the glove box.

## The Final Verification

Keeping a backup on the same OVH machine protects against mistakes.

It does not protect against the OVH machine dying.

So I copied the portable recovery bundle, its checksum, the Windows host configuration, and its checksum off the server.

Then I verified everything again from the off-host copies.

The results:

- both external SHA-256 files matched
- the TAR/GZIP structure passed
- the host ZIP and all 12 files inside it passed
- every checksum inside the portable bundle passed
- the nested persistent-data archive passed
- all 102 persistent entries were present
- the PostgreSQL dump matched the exact copy already validated by `pg_restore`

At this point I am comfortable calling it a real backup.

Not a file named `backup-final-final-2` sitting on the same disk.

Not a mystery database dump I have never opened.

Not a vague belief that Kubernetes probably keeps this stuff somewhere.

A documented, hashed, structurally verified, off-host recovery package.

## What Recovery Should Look Like

If the server dies, the intended path is now:

1. Install the Funcom self-hosted server tool on a clean machine.
2. Recreate the Hyper-V switch, NAT, firewall rules, and VM network.
3. Run the Funcom setup once with a valid token.
4. Recreate the real battlegroup identity and specification.
5. Keep the game servers stopped.
6. Import the saved PostgreSQL database through Funcom's supported importer.
7. Restore the live `UserEngine.ini` and `UserGame.ini`.
8. Start the battlegroup.
9. Verify characters, inventories, bases, vehicles, world state, and server tuning.
10. Make another backup immediately.

That process still needs a full rehearsal in a disposable VM.

I am not declaring victory over disaster recovery until I have actually rebuilt the server somewhere else and watched our bases appear.

But the important data is finally captured in a form designed for that test.

## Arrakis Is Sleeping

For now, the battlegroup is stopped.

The VM is powered off.

At least while it is off, no game process is actively ticking the base power down.

The world database is backed up.

The live settings are backed up.

The Windows host configuration is backed up.

The recovery files are verified and stored off-host.

The giant unnecessary VM clone is sitting nearby like a 97 GB emotional-support animal.

There is also a new Funcom build waiting for me.

Eventually I will bring the server back, update it, and start another deep dive into every exposed setting and every setting we managed to expose ourselves.

That will become its own guide because I would very much like to stop rediscovering the acceptable values for obscure Dune server variables through trial, error, cooked assets, database archaeology, and vibes.

But that is a problem for future me.

Present me successfully turned off Arrakis without losing it.

That is enough infrastructure for one day.
