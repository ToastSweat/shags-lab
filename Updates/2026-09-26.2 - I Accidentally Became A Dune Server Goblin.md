# I Accidentally Became A Dune Server Goblin

This started because I wanted a private Dune server.

That seems simple enough.

Install the dedicated server.
Set a password.
Invite friends.
Run around Arrakis.
Try not to get eaten by the worm.

Naturally, I ended up learning about SteamCMD, Hyper-V networking, Windows NAT, Kubernetes pods, container images, UDP port ranges, memory limits, broken upstream builds, and the emotional burden of naming an internal switch `Bootyhole`.

This happens to me a lot.

The server is for Dune: Awakening, which has a self-hosted server tool.

The normal game is Steam app:

```text
1172710
```

The self-hosted server tool is:

```text
4754530
```

That distinction matters because the first rule of running a dedicated server is apparently:

> Make sure you are installing the server.

Inspiring.

The install itself lives on my dedicated Windows server.

I already use this machine for other nonsense, because apparently I have decided that “fun hobby” means “becoming my own underpaid infrastructure department.”

The Dune server went into:

```text
C:\PGN\DUNE
```

SteamCMD went into:

```text
C:\PGN\STEAMCMD
```

I learned very quickly to avoid cute folder names with brackets.

Something like:

```text
C:\[PGN]\[DUNE]
```

looks organized until PowerShell and scripts start treating brackets like they are part of an ancient curse. Thanks [[Multi Theft Auto]].

So now it is boring paths only.

Boring paths are beautiful.

The first big wall was networking.

The server runs inside a self-hosting VM, and my first instinct was basically:

```text
Make VM.
Give VM internet.
Profit.
```

Unfortunately, OVH dedicated servers and Hyper-V bridged networking do not care about my instincts.

The VM was alive.
The host was alive.
The network was allegedly alive.
The server was not meaningfully reachable.

The clean solution ended up being an internal Hyper-V switch with Windows NAT.

The working switch is named:

```text
Bootyhole
```

I will not be taking questions at this time.

The VM sits at:

```text
192.168.69.69
```

because if I am already debugging haunted UDP traffic on a private Arrakis server, I am at least going to entertain myself.

The final network path is:

```text
Internet
→ Windows Server
→ Windows Firewall
→ Windows NAT
→ Hyper-V Internal Switch
→ Dune VM
→ Kubernetes
→ Dune game server pods
```

That is a lot of arrows for “play video game with friends.”

The official ports were not the whole story either.

The obvious range was:

```text
7777-7810 UDP
```

plus:

```text
31982 TCP
```

But the setup did not fully behave until we also forwarded the inter-server gateway range:

```text
7888-7921 UDP
```

Before that, the server could get weirdly close to working.

Visible enough to taunt me.
Not connected enough to play.

That is worse than simply being broken.

A server that is completely broken is honest.

A server that appears in the browser and then refuses to connect is a butthead.

Eventually, the network behaved.

The server appeared.
The password prompt worked.
I could join.

Victory.

For about five minutes.

Then came tuning.

The Dune self-hosting setup uses config files named:

```text
UserEngine.ini
UserGame.ini
```

These apply across the battlegroup unless you override things per server in the battlegroup editor.

I set the server name.
I set the password.
I played with mining multipliers.
I looked at sandstorms, worms, deterioration, PvP zones, land claim settings, all the usual private server temptations.

You start with:

> I just want a chill server for friends.

Then ten minutes later you are staring at:

```ini
Vehicle.SandwormInvulnerabilitySecondsOnServerRestart=7200.0
```

like some kind of discount Arrakis systems administrator.

At one point I wanted to enter a special area and the server just refused.

This turned out to be a memory limit issue.

The pod for that area had been getting:

```text
OOMKilled
Exit Code 137
```

It had a `5Gi` memory limit.

I gave it more memory, restarted the battlegroup, and it worked.

That one was satisfying because it was a real problem with a real answer.

Area broken.
Pod killed for memory.
Increase memory.
Area works.

Beautiful.

Computers almost never give you that kind of clean emotional closure.

Then the server disappeared.

I logged in one morning and did not see my server in the list.

The battlegroup status screen was also suspicious.

The infrastructure looked fine.

Database? Fine.
Gateway? Fine.
Director? Fine.

But the actual game server rows were blank.

No map names.
No phase.
No useful status.

That is when things became less “private server setup” and more “I am reading Kubernetes entrails at breakfast.”

Inside the VM, the real battlegroup namespace was:

```text
funcom-seabass-sh-238803c537a22e2-fdofyf
```

There was also a second, unused battlegroup namespace:

```text
funcom-seabass-sh-238803c537a22e2-krmfhh
```

That second one later got deleted, but at this stage I did not want to touch anything until I knew which pile of letters contained my actual world.

The real one was `fdofyf`.

I checked the pods.

The infrastructure pods were running.

The actual playable servers were not.

Overmap and Survival were both in:

```text
CrashLoopBackOff
```

The describe output showed:

```text
Exit Code 139
```

That is not a happy exit code.

The previous logs had the real clue:

```text
Failed to load data table property 'm_SpiceFieldTypeDataTable'
```

and:

```text
/Game/Dune/Systems/SpiceHarvesting/DT_SpiceFieldTypes
```

Then the server caught:

```text
Signal 11
```

and fell over.

So the game server was trying to load a Spice Harvesting data table that was not there.

Which, for a Dune game, feels like a pretty unfortunate thing to misplace.

I checked my config files.

Nothing.

No `SpiceHarvesting`.
No `DT_SpiceFieldTypes`.
No `m_SpiceFieldTypeDataTable`.

I searched `/home/dune`.
I searched `/funcom`.
I checked disk space.

Disk was fine.

The bad path was not in my visible config.

So naturally I did the ancient ritual:

```text
Maybe update fixes it.
```

It did not.

At first, the update just re-applied the same build:

```text
2007976-0-shipping
```

I removed and reimported the game server container image.

Still broken.

The same crash.
The same missing Spice table.
The same blank status rows.

At that point, the evidence was pretty clear:

```text
This was not my network.
This was not my ports.
This was not my config.
This was not disk space.
This was not the VM being haunted.
```

Funcom had pushed a bad self-host build.

Honestly, that was kind of a relief.

It is annoying when something is broken upstream, but it is also nice to stop gaslighting yourself with port forwarding rules.

I sent an email through the Funcom site.

Discord pointed me that way.

Eventually, Funcom fixed the build.

It did not fix itself automatically.

A normal restart did not fix it.

I had to run the server update again, pull the corrected build, and restart the battlegroup.

Then everything came back.

Actual game rows.
Actual status.
Actual server visibility.
Actual joy.

Once the real server was healthy, I cleaned up the unused battlegroup.

The dead one was:

```text
sh-238803c537a22e2-krmfhh
```

It had no resources, no useful running server, and no future except confusing me later.

So I deleted its namespace.

The real one remains:

```text
sh-238803c537a22e2-fdofyf
```

That is the world.

Do not delete the world.

That should probably be written on a sticky note above the server.

This project now has a proper doomsday guide because there is absolutely no chance I am rediscovering all of this from scratch six months from now.

The guide covers:

```text
SteamCMD
Dune app IDs
Hyper-V setup
Windows NAT
Firewall rules
Required port ranges
Battlegroup setup
UserGame.ini
UserEngine.ini
Backups
Kubernetes commands
CrashLoopBackOff troubleshooting
OOMKilled fixes
Bad Funcom build symptoms
Deleting unused battlegroups safely
```

Basically everything future me needs when something explodes and present me is not around to explain why the private switch is called `Bootyhole`.

What did I learn?

I learned that self-hosting modern games is not just “run server.exe.”

It is a stack.

A weird stack.

A Windows host runs a Linux VM that runs Kubernetes that runs containers that run the game servers that talk through gateways that depend on RabbitMQ and a database and a director and a handful of UDP ports that all need to agree about reality.

That sentence is exhausting.

I also learned that a server can be broken in at least six completely different ways:

```text
Wrong Steam app
Bad install path
Bad VM networking
Missing NAT mapping
Low memory limit
Bad upstream build
```

And each one looks like:

```text
Server no work
```

Very helpful.

But now it works.

The server is up.
The bad battlegroup is gone.
The network setup is documented.
The weird Funcom build failure is documented.
The recovery path is documented.

And most importantly:

```text
Bootyhole lives.
```

Not bad for wanting to play Dune with friends.
