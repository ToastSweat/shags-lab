I wanted to fix the Image Ranker showing me the same stuff, and open it up so I could use it from my phone.

I also said I expected that to be an easy task.

That was optimistic.

The [[Projects/Corsair Xenon Edge/iCue Image Ranker Widget/iCue Image Ranker Widget Home|Image Ranker]] has been working pretty well. It sits on the [[Projects/Corsair Xenon Edge/Corsair Xenon Edge Home|XENEON EDGE]], shows me a pair of images or videos, and asks which one I like better.

I tap a winner. The ratings update. Another pair appears.

A completely reasonable use of a touchscreen attached to an unreasonable archive.

It works alongside the [[Projects/Booru Image Downloader/Booru Image Downloader Home|Booru Image Downloader]], which handles the downloading and tag folders. The ranker leaves those files alone and keeps its own voting history.

The problem was that after using it for a while, I started recognizing the contestants a little too well.

## The usual suspects

It felt like I was constantly ranking the same ten or fifteen images.

I liked those images. That was how they got there.

But I also had a fairly large collection of other images that were presumably wondering whether they had applied to the wrong tournament.

When [[Wiki/Hermes Agent|Hermes]] checked the history, this was not just me imagining things. Some exact pairs had come up around fifty times, while hundreds of thousands of images still had no votes.

The old selection logic mixed discovery with comparisons between strong contenders. That sounded sensible. Unfortunately, the strong-contender side kept returning to a very small group near the top.

I had built a machine that could develop favorites and then refuse to change the subject.

We changed that.

The current defaults give an exact pair a rest for 500 comparisons, and give individual images a rest for twelve. The refinement pool is broader too, rather than mostly letting the top ten argue among themselves.

Discovery gets more of the attention now.

Those cooldowns are not a promise to invent new images if somebody points it at a folder containing two files. Small collections have to repeat eventually. The important part is that a large archive should not behave like a very small archive with an impressive folder size.

My existing ratings and voting history stayed intact. The current unanswered pair stayed put too. Changing how the next pair gets selected is not a good reason to throw away the question already on the screen.

The favorites view is also Top 100 now, with five items per page.

I wanted more favorites. I did not want a hundred videos trying to play on the little monitor simultaneously.

There are limits to my commitment to this idea.

## Obviously this needed to be on my phone

The other request was pretty simple.

Sometimes I want a mindless thing to do on my phone when I am bored. Apparently tapping through an archive and making increasingly specific judgments about it qualifies.

The desktop already had a browser view, so the initial thought was basically:

```text
The PC has a website.
The phone has a browser.
They are on the same Wi-Fi.
This should be fine.
```

There were a few details hiding inside "fine."

The normal companion was deliberately listening only on localhost. I did not want to solve phone access by casually exposing the whole archive API, its key, or the rankings database to the network.

So the phone gets a separate gateway.

I open its local address, enter a one-time code from the PC, and get a phone-sized version of the ranker. The gateway handles the private connection to the companion. The phone does not need the core API key copied into its address bar or settings.

Votes still go into the same database. The phone and the monitor are looking at the same ongoing comparison, rather than quietly developing two incompatible opinions about my taste.

The phone layout has proper touch targets, Retry and Skip, the paged favorites view, and a Disconnect button. Video remains muted.

That last part was not negotiable.

This is for trusted home Wi-Fi. It is still HTTP, so pairing does not magically make the traffic encrypted. The PC has to stay awake, and I am not opening a router port so the Internet can participate.

I have enough opinions to process already.

Then I tried it on the actual phone.

## The phone disagreed

Chrome could not reach the site.

The PC could.

The gateway was running. The address was correct. The narrowly scoped firewall rule was there. The phone and PC were on the same subnet, and the PC could ping the phone.

Chrome was producing `ERR_TOO_MANY_RETRIES`, which is an excellent error message if your goal is to make somebody feel that more retries would be an unreasonable request.

We checked local-network permissions. Restarted Chrome. Looked for a VPN or filtering app. Captured connection headers to see whether the attempts were even reaching the PC.

They were not showing up.

I am not going to claim we solved Chrome. We did not.

I downloaded Firefox instead, and the pairing page appeared.

Progress.

I entered the code.

The next page started loading.

Then the whole thing got stuck and eventually reported that the connection had been reset.

Now the gateway had also stopped answering requests from the PC.

That was a useful distinction. We had gone from a browser-specific access problem to a server that had stopped doing its one fairly important job.

## Please do not select the server

The cause of that second failure was ridiculous.

The Windows console running the gateway was in Select mode.

Text was highlighted in the console window.

That was enough.

Pairing consumes the old code and generates a new one. The gateway then announces that new code in its console. With the console sitting in Select mode, that output could block.

The print happened before the pairing response finished.

So the sequence was effectively:

```text
Accept pairing code
Generate next code
Try to print next code
Wait for Windows console selection
Forget to finish being a website
```

I had given the server a dependency on whether somebody was highlighting a number.

Very advanced architecture.

The fix was to stop making the long-running network process depend on an interactive console at all.

The gateway now starts independently, with its output going to private log files. A small launcher shows the address and current code, then exits. I can copy that output or close the viewer without interfering with the service.

If I need the current code again:

```text
npm run phone:code
```

That command is just a viewer. It is not the server.

Stopping phone access also has its own command now, which checks that it is stopping this project's gateway rather than taking an optimistic guess at a process ID.

The normal ranker keeps running separately.

We tested pairing and code rotation again. Then I went back to Firefox on the phone.

The comparison view finally loaded.

On the actual phone.

That test turned out to be worth doing.

## Back to wasting time productively

The selection changes are running, the phone can connect, and my voting history survived the whole exercise.

The ranker should spend less time asking me to reconfirm the same handful of favorites. I can browse the Top 100, rank new candidates from the phone, and explicitly skip something that will not load without pretending I voted against it or deleting a source file.

The downloader still does its own thing. The archive is still read-only as far as the ranker is concerned.

Firefox is the browser I am using for this on the phone for now. Chrome can keep its mystery until I feel like investigating that particular personality trait again.

The code is in [icue-image-ranker](https://github.com/ToastSweat/icue-image-ranker), with the local-network setup documented separately. Anyone building their own copy gets their own configuration and private key; my generated packages and rankings do not belong in the public repo.

I started this update because the ranker was showing me the same pictures too often.

Now it shows me more pictures, on another device, and I have learned that selecting text can be a networking problem.

I would have preferred to learn that last part from somebody else's project.
